# The 3B's K-line diagnostics (KW1281, early dialect) — traced 2026-09-09

*Source: `roms/3b_fuel-ign_404aa.bin` (447907404AA). The responder code is
byte-identical on the 3B 404A, the RR 857907404B and the S2 895907404; the
descriptor table differs by one byte (+A1) on the 3B-A and RR.*

## Why this matters

Ross-Tech's `85-01.lbl` redirect names a `447-907-404.LBL` "(2.2l @ 220 HP
- 3B/RR)" that was never shipped, so VCDS shows this ECU without labels and
KWPBridge had no definition for it. The firmware itself tells us what the
ECU can say on the K-line, and it is not the later VAG layout.

## Identification (title 0xF6, five blocks)

Sent by handler 2 (`0x3D3A`) from the ID string at `0x7F01`:

| block | bytes | source | 3B AA text |
|---|---|---|---|
| 1 | 12 | `0x7F02` | `447907404 AA` |
| 2 | 12 | `0x7F0E` | `   MOTOR    ` |
| 3 | 4 + n | `0x7F1A` + coding | `PMC ` then the **coding number** (`9Eh`, 1…27) as ASCII digits, computed by calling the coding routine `0x3637` (docs 3f) |
| 4 | 10 | `0x7F1E` | `0261200451` (Bosch number) |
| 5 | 10 | `0x7F28` | `1267356462` (ROM number) |

So a plain VCDS or KWPBridge identification read shows the coding class
without touching the plug pins.

## Protocol descriptor

`LCALL 0x3408` sets `DPTR = 0x6407` (or `0x64DE` when bit `21h.0` is set,
the boost-board config line). The table holds the request titles the ECU
recognises (`+00…+13`), the response titles it uses, timing constants, the
fault "elaboration" byte table (`+36`) and the group-000 read list (`+BC`):

```
+00: 00 01 02 03 04 05 06 07 08 09 0A 11 12 | FE FD FC FB F6 F5 F4
      ^request titles (index = handler)       ^response titles
+BC: 0A | 00 38 | 00 3F | 00 3B | 02 3F | 02 4F | 02 47 | 02 51 | 02 0F | 02 07 | 00 53
```

Request → handler → response (dispatch at `0x4349`…`0x45D4`, handlers from
`0x3D32`):

| request title | handler | response | what it does |
|---|---|---|---|
| `0x00` | 2 | `F6` ×5 | (re)send identification |
| `0x01` read RAM `[n, page, addr]` | 5 | `FE` | ≤13 bytes; page 0 = internal RAM, 1 = ports P1/P3/P4/P5, ≥2 = XRAM page (page−2). Repeated calls page through longer requests |
| `0x03` read ROM `[n, hi, lo]` | 6 | `FD` | `MOVC` from code space |
| `0x04` actuator test | 0x0C | `F5` | walks the output list, reports E1/E2/E4/E5/E3/E9/DF/EE |
| `0x05` clear DTCs | 3 | `09` ACK | |
| `0x06` end | — | — | `0x4168` re-init |
| `0x07` read DTCs | 9 | `FC` | 3-byte entries `[code, elaboration(+36 table), status]` from the fault list at XRAM `0x0200` (5 bytes per fault, count in XRAM `E5h`), four per block |
| `0x08` read ADC `[ch]` | 7 | `FB` | one ADC conversion of channel `ch` via `0x135D` |
| `0x11` basic setting `[g]` | 0x0D | `F4` | sets XRAM `68h.6` (basic-setting mode), then the same 10-byte block |
| `0x12` group read `[g]` | 0x0D | `F4` | the 10-byte block below, **whatever `g` is** |

There is **no `0x29`/`0x28`** and **no `0xE7` formula response**: this ECU
predates the four-cell measuring blocks. It has one group, "000", and it is
the raw ten-byte block.

## Group 000 — the ten bytes

Handler `0x0D` (`0x40CB`) reads the list at descriptor `+BC`
(`0x64C3`): `[count][type, addr]…`, type 0 = internal RAM, 1 = port, ≥2 =
XRAM page. Same list on every 404 chip we have.

| # | source | meaning | decode | note |
|---|---|---|---|---|
| 1 | RAM `38h` | coolant temperature | raw × 0.75 − 48 °C | ECT input of the maps |
| 2 | RAM `3Fh` | engine load | raw | **the fuel/ignition map load axis unit** (3B axis 14…190) |
| 3 | RAM `3Bh` | engine speed | raw × 10 rpm | `3Bh = 3Ah << 2` (`0x1C79`…`0x1C8D`); saturates at 255 = 2550 rpm |
| 4 | XRAM `0x3F` | idle stabiliser range | raw | |
| 5 | XRAM `0x4F` | idle stabiliser zero point | raw | |
| 6 | XRAM `0x47` | idle stabiliser load adjustment | raw | |
| 7 | XRAM `0x51` | idle stabiliser control | raw | |
| 8 | XRAM `0x0F` | lambda control | raw, 128 = no correction | |
| 9 | XRAM `0x07` | lambda adaptation | raw, 128 = no correction | |
| 10 | RAM `53h` | ignition timing | raw × 0.75 − 22.5 °BTDC (assumed, map units) | `53h` = final timing after corrections (`0x17C2`); `54h` = base |

The order and meaning match the "Group 000" list Paul Nugent left in the
ABY label for reference, which is the same Bosch convention.

## What KWPBridge does with it

- `ECU_M23_3B` in `kwpbridge/ecu_defs.py` (part numbers 447907404AA/A,
  857907404B, 895907404/A): `group_read_title = 0x12`, `raw_groups[0]` with
  the decodes above.
- Pseudo-group **100**: a read-RAM window (`0x01`, page 0) over `36h…3Fh`
  and `53h…54h`, so live data arrives as UBAT `36h`, IAT `37h`, ECT `38h`,
  **RPM `3Ah` × 40 (no saturation)**, **LOAD `3Fh`**, timing `53h`/`54h`.
  That is exactly what UrROM's map overlay needs: the same units as the
  map axes.
- `labels/modules/447-907-404.lbl` is the file Ross-Tech's redirect wanted.
- Mock: `python -m kwpbridge.mock --ecu 3b`.

UrROM's `LiveValues` recognises the 404 family (part number or the
presence of group 100) and takes group 100 first, group 0 as fallback.

## Open items

- Baud rate and the exact 5-baud/sync handshake are untested on a car
  (9600 assumed, as for the other Bosch M2.3.x units).
- The `53h` decode (map units) is the natural assumption, not yet checked
  against a timing light.
- Actuator-test and fault-code tables are not decoded (generic DTC text).
